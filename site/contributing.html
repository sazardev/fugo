Contribuir a Fugo

Fugo es un proyecto abierto bajo licencia MIT. Esto es todo lo que necesitas para configurar el entorno, seguir el estilo de código y abrir un pull request que pase la puerta de CI a la primera.

Hacer fork en GitHub Ver issues abiertos

Antes de empezar

Lee primero CLAUDE.md en la raíz del repositorio — es el documento de arquitectura canónico (paquetes, flujo de datos, formato de cable, convenciones) y se mantiene al día con el código, a diferencia de algunos documentos de diseño más antiguos en español bajo ROADMAP/.

Para cualquier cambio no trivial (un widget nuevo, un cambio de transporte, un comando de CLI), abre primero un issue o discussion — ahorra retrabajo si el enfoque necesita ajustes. Fixes pequeños (typos, docs, un bug claro con test de regresión) pueden ir directo a un PR.

Entorno de desarrollo

Requiere Go 1.26+. Los bindings de protobuf generados están commiteados, así que go build ./... funciona de inmediato sin protoc.

git clone https://github.com/sazardev/fugo && cd fugo
make install        # instala los git hooks de Lefthook
go build ./...
make test            # go test ./... -count=1 -race -shuffle=on -v

Si vas a tocar transport/proto/fugo/v1/fugo.proto, además necesitas protoc, protoc-gen-go, protoc-gen-go-grpc y protoc-gen-dart (el plugin de Dart debe ser protoc_plugin 21.1.x — ver CLAUDE.md).

Si vas a tocar flutter_client/ (el cliente Dart), necesitas el SDK de Flutter fijado en FLUTTER_VERSION — ver flutter_client/README.md.

Estilo de código

  • El formateador es gofumpt, no gofmt — corre gofumpt -w . antes de commitear (Lefthook lo hace automáticamente en los archivos en stage)
  • make lint corre golangci-lint (80+ linters en .golangci.yml) y staticcheck — ambos deben pasar limpio, sin umbral de tolerancia
  • make vet (go vet ./...) debe pasar
  • Cambios acotados: un bug fix no debería traer un refactor sin relación. Sin abstracciones especulativas para necesidades hipotéticas futuras
  • Los widgets siguen las convenciones de fg/: constructores sin prefijo (fg.Text, no NewText), setters encadenables, una bandera *Set bool para props opcionales

Tests

make test corre la suite completa con -race -shuffle=on. El código nuevo necesita cobertura de tests; los bug fixes necesitan un test de regresión que falle antes del fix y pase después.

Los tests table-driven son el estilo de la casa en el lado Go. Los benchmarks viven en *_bench_test.go (engine/ tiene las puertas de rendimiento que CI verifica en cada push — no las regresiones sin una buena razón documentada en el PR).

Commit & pull request

  1. Crea una rama a partir de main.
  2. Haz tu cambio, con commits acotados.
  3. gofumpt -w ., make lint, make vet, make test, go mod tidy — todo limpio.
  4. Actualiza CHANGELOG.md bajo [Unreleased] si el cambio es visible para el usuario.
  5. Abre el PR — .github/pull_request_template.md te pedirá el checklist anterior. make pr MSG="type: description" automatiza el branch/push/apertura del PR si estás trabajando directo desde main.

CI corre lint, vet, build, test (-race -shuffle=on), un chequeo de formato con gofumpt, el perf gate/benchmarks, y el job de Dart (flutter analyze + flutter test) en cada push y PR — todo debe pasar antes de mergear. CodeQL corre semanalmente y en cada push para análisis de seguridad.

Releases

No edites a mano VERSION, FLUTTER_VERSION, ni CHANGELOG.md — son responsabilidad de quien mantiene el proyecto vía make release / make release-flutter. Ver el esquema de versionamiento para los detalles.

Reportar bugs / seguridad

Usa las plantillas de issue — piden el contexto correcto de entrada (pasos de reproducción, versiones de Go/Flutter, comportamiento esperado vs. real).

Para vulnerabilidades de seguridad usa un security advisory privado en lugar de un issue público — ver SECURITY.md.

Código de conducta

Este proyecto sigue el Contributor Covenant. Al participar, se espera que lo respetes.
