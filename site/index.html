Qué es Fugo

Fugo es un framework local de Server-Driven UI (SDUI): construyes aplicaciones de escritorio nativas escribiendo exclusivamente en Go. La lógica de negocio, el estado y el enrutamiento viven enteramente en un proceso Go; un motor Flutter precompilado actúa como una terminal de renderizado pura — sin lógica de aplicación, sin estado propio.

Los dos procesos se comunican por gRPC con streaming bidireccional, sobre Unix Domain Sockets (TCP en Windows) y Protocol Buffers como formato de cable.

┌──────────────────────┐     IPC (UDS/TCP)    ┌──────────────────────┐
│      Proceso Go      │◄════════════════════►│   Proceso Flutter    │
│                      │   gRPC + Protobuf     │                      │
│  Lógica de negocio    │                       │  Registro de widgets │
│  Árbol retenido       │──── Diff de árbol ───►│  Pipeline de render  │
│  Motor de diffing     │                       │  Debounce de eventos │
│  Servidor gRPC        │◄──── Eventos de UI ───│  Cliente gRPC        │
└──────────────────────┘                       └──────────────────────┘

Go es la fuente de verdad absoluta. Flutter es una terminal muda: sin lógica de negocio, sin estado — solo píxeles a 60/120 fps vía Impeller.

Objetivo

Fugo busca ser el framework "pilas incluidas" para construir aplicaciones de escritorio ultrarrápidas y eficientes usando únicamente Go: aplicaciones corriendo en segundos, combinando la velocidad de iteración y el conocimiento que ya tienes de Go con el poder de renderizado y el ecosistema visual de Flutter — sin tener que aprender Dart, sin gestionar estado en dos lenguajes, sin el consumo de memoria de un motor basado en Chromium.

No es un puente genérico Go↔Dart ni un binding de FFI: es una arquitectura deliberada de terminal tonta donde el 100% de la superficie de programación que tocas es Go — fg.Text, fg.Button, fg.Router — y Flutter nunca ve una decisión de negocio, solo un árbol de widgets y sus parches.

Para quién

Desarrolladores Go

Que quieren una GUI de escritorio nativa sin salir de Go ni aprender Dart/Flutter para poder usarlo.

Herramientas internas

Equipos que ya tienen backends/CLIs en Go y necesitan una interfaz de escritorio ligera para operarlos, sin el peso de Electron.

Apps de un solo lenguaje

Proyectos donde mantener un único lenguaje de aplicación (Go) es una prioridad de arquitectura y de equipo, no una preferencia estética.

Cómo funciona

El árbol de widgets se construye una sola vez y se retiene. Los manejadores de eventos son closures de Go que mutan los campos del widget directamente (counterText.SetText("5")) y luego llaman a ctx.Update(). El scheduler (ticker de 60 fps) vuelve a recorrer ese mismo árbol cada frame cuando hay cambios pendientes, re-serializa las props, calcula el diff contra el snapshot anterior y transmite solo los parches.

Esto no es un "rebuild desde cero" al estilo React — es mutación directa de un árbol retenido, con diffing por ID/posición (CREATE/UPDATE/DELETE/REPLACE/REORDER) y streaming incremental sobre gRPC.

Estado y progreso

v3.44.8-fugo.0 — el motor, la API de widgets, el transporte, el supervisor de proceso, el CLI y el cliente Flutter están implementados y funcionan de extremo a extremo.

  • Instalable vía go install github.com/sazardev/fugo/cmd/fugo@latest — los bindings de protobuf están commiteados, compila en un fetch limpio
  • Material 3 nativo (claro por defecto), variantes de botón, Card/Scaffold/FAB/ListTile/Chip/Progress
  • Motor de diffing, reconciliador, scheduler de 60 fps con prioridad (Update / UpdateNow)
  • Transporte gRPC (UDS / TCP en Windows), health check, keepalive, token de autenticación opcional
  • 83 widgets en fg/ con API fluida y prefix-free, un sistema de Theme, y un fg.Store[S] opcional para estado compartido
  • Cliente Flutter (isolate gRPC en segundo plano, registro de widgets, reconexión automática)
  • CLI: fugo init / run (hot reload por defecto) / build / doctor (--fix) / widgets / upgrade
  • Control de ventana en tiempo de ejecución, portapapeles, diálogos de archivo nativos
  • Overlays imperativos: ShowSnackBar, ShowDialog, ShowBottomSheet, selectores de fecha/hora
  • Rendimiento: diffing con pool de objetos, ajuste de GC, benchmarks Go + Dart con perf gate en CI

Ver ROADMAP y SPEC.md para la visión de diseño completa.

Alcance

Dentro del alcance

  • Apps de escritorio: Linux, Windows, macOS
  • IPC estrictamente local (UDS/TCP en 127.0.0.1)
  • Un binario Go + un cliente Flutter precompilado por plataforma
  • Material 3 como sistema de diseño del cliente de render

Fuera del alcance (por ahora)

  • Móvil (iOS/Android) y web
  • SDUI remoto sobre red (el diseño asume IPC local de baja latencia, no una WAN)
  • Persistencia de estado entre hot reloads (el estado en memoria se reinicia)
  • Un sistema de diseño propio — el cliente es intencionalmente Material 3 "vanilla"

Ventajas y desventajas

Ventajas

  • Sin el consumo de memoria de Electron/Chromium — renderizado nativo vía Flutter/Impeller
  • Un único lenguaje de aplicación: toda la lógica, el estado y el enrutamiento en Go
  • Material 3 real (tipografía, layout, animaciones) sin reinventar un design system
  • Latencia de IPC local de 5–10µs, no 50–200 ms de un SDUI remoto
  • Solo se transmiten diffs — el framing en Protobuf evita el costo de parsear JSON en cada frame
  • CLI "pilas incluidas": init → run (hot reload) → build → doctor

Desventajas

  • Pre-1.0: la API pública puede tener cambios incompatibles entre versiones
  • fugo run/build requieren el SDK de Flutter instalado (o un binario precompilado vía FUGO_FLUTTER_BINARY)
  • Sin objetivo móvil o web todavía — desktop-only por diseño actual
  • El hot reload no persiste el estado en memoria entre recargas
  • Ecosistema y comunidad jóvenes — menos respuestas de terceros que con Flutter/Dart puro
  • Estás limitado a la superficie que expone fg/, no al 100% de los widgets de Flutter/Dart

Seguridad

El transporte es local por defecto — Unix Domain Sockets (o TCP en 127.0.0.1 en Windows) — no expuesto a la red salvo que el usuario lo configure explícitamente. FUGO_AUTH=1 añade un token por ejecución que endurece aún más el transporte local.

Código abierto y contribución

Fugo es abierto a contribuciones bajo licencia MIT. El flujo de trabajo está documentado en CONTRIBUTING.md y el proyecto sigue el Contributor Covenant.

  • Plantillas de issue estructuradas (bug report / feature request) y de pull request
  • CODEOWNERS define la revisión requerida en todo el repositorio
  • .golangci.yml: 80+ linters activos, sin umbral de tolerancia (max-issues-per-linter: 0)
  • Git hooks (Lefthook): pre-commit auto-arregla formato/lint; pre-push corre la puerta completa
  • Dependabot semanal para módulos Go y GitHub Actions

CI/CD

Todo push y pull request a main corre la misma puerta de calidad — nada se fusiona sin pasarla:

Lint

golangci-lint + staticcheck

Vet

go vet ./...

Build

go build ./...

Test

go test -race -shuffle=on

Format

gofumpt, sin diferencias

Bench

Perf gates + benchmarks del motor de diffing

Dart

flutter analyze + flutter test en flutter_client/

CodeQL

Análisis de seguridad, push/PR + semanal

Aparte, check-flutter-version.yml vigila semanalmente nuevas versiones estables de Flutter y abre un PR (nunca auto-merge) para actualizar el pin, y release-flutter-client.yml compila el cliente Flutter para Linux/Windows y lo adjunta al release en cada tag v*.

Esta misma página se despliega automáticamente: un workflow de GitHub Actions publica site/ en GitHub Pages en cada cambio a main, sin pasos manuales.
